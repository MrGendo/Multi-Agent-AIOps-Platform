## 一、评测设计

**样本来源**: Suricata EVE JSON 取自官方文档真实样本(dotted-quad POST 告警); 其余按
Wazuh/Falco/CEF 官方格式构造, 注入真实攻击特征(真实 CVE、真实规则 ID 5720/31151、
真实恶意软件家族 xmrig、MITRE 技术)。IP 采用 RFC5737/5737 文档保留段(203.0.113.x 等)
— **这个选择后来被证明影响了 T09, 见第四节**。

**维度覆盖**:

| 维度 | 覆盖情况 |
|------|---------|
| 输入格式 | Suricata EVE ×2 · Wazuh JSON ×2 · Falco JSON ×2 · CEF ×2 · 自由文本 ×2 · 邮件 .eml ×2 |
| 攻击类型 | C2 外联 · 漏洞利用(Log4Shell) · 暴力破解 · SQL 注入 · 反弹 Shell · DGA C2 · XSS · 挖矿 |
| 阴性对照 | 容器正常运维操作(Falco) · 正常 VPN 登录(CEF) · 正常业务邮件 |
| 评估指标 | 域分流 · verdict 四态 · IOC 提取 · MITRE 映射 · 流程完整性 · 置信度 · 时延 |

## 三、分维度分析

**1. 域分流(10/12)**: 五种厂商格式全部正确进入安全域。阴性对照 T08 被分到运维域并
自动转投 AIOps 诊断 — 合理且是设计行为(正常登录属运维事件, 无安全误报)。
**唯一失误 T10**: 挖矿告警的文本特征(EDR/进程/CPU 97%/crontab)全是运维词,
「挖矿/xmrig/矿池」未触发安全分流 → 整条告警进了诊断流水而非安全研判。
**分流器的关键词体系偏网络侧(WAF/IDS/告警/攻击), 主机侧安全特征(挖矿/后门/持久化/恶意进程)覆盖弱。**

**2. 判定四态(9/11)**: 阳性 7 例中 6 例正确且分级合理 — 高危明确攻击(反弹 Shell 0.90、
Log4Shell 0.85、暴破 0.85、DGA C2 0.75)给 malicious, 证据相对单薄的(T01 单规则命中 0.45、
T04 单次注入尝试 0.60)给 suspicious — **判定与证据强度匹配, 无小题大做也无漏报**。
阴性 3/3 全对, 无一误报。

**3. IOC 提取(9/9)**: 全部安全域案例的 must-have IOC(源/目的 IP、CVE-2021-44228)
100% 提取, 包括从 URL、命令行、CEF 扩展字段等不同位置。

**4. MITRE 映射(7/7)**: 全部命中预期技术号且合理扩展(如 T05 反弹 Shell 除 T1059 外
补充 T1095 非应用层协议、T1204 用户执行、T1583 基础设施获取)。

**5. 邮件研判(2/2)**: E01 phishing 0.97 + credential_phishing 细分 + 3 条确定性信号
(Reply-To 异域/Return-Path 异域/仿冒域名)+ 3 条 LLM 指标, E02 benign 0.95 —
邮件管线判定质量与速度(25-30s)均优于告警管线。

**6. 时延**: 深查路径 160-350s(五阶段 + Critic 重试, GLM 限流时翻倍); 快速通道(噪声
拦截)11.5s; 邮件 25-30s。深查时延主要消耗在 LLM 串行调用 + 429 退避。

## 四、发现的问题(按严重度)

### 4.1 [高] 主机安全类告警分流缺陷(T10)
挖矿(EDR 场景)被运维关键词劫持分流。同类风险: 后门/持久化/恶意进程/勒索加密等
主机侧特征词可能同样漏分。**已修 (2026-11-03)**: 关键词表补充 10 个主机侧特征词 (xmrig/矿池/可疑进程/恶意进程/
恶意文件/病毒/virus/反弹shell/reverse shell/shellcode); 初版含 wallet/持久化/persistence,
经 pr-reviewer 实测误伤支付与存储运维告警 (平局劫持) 后收窄删除。T10 回归 2:1 正确分流。

### 4.1b [新观察] 修复后 T10 判定过度保守
分流修复后 T10 进入安全研判, 但 verdict=inconclusive(置信 0.135)。教科书式挖矿特征
(xmrig 进程 + 钱包参数 + 矿池外联 + crontab 持久化)齐全, LLM 因外部情报无法佐证
(评测用假域名, 情报源 502)而给极低置信度 — **本地行为特征已足定性时过度依赖外部情报确认**。
与 4.2 同源: 证据权重偏外证轻内证。属提示工程调优项, 暂不修, 记录备考。

### 4.2 [中] 判定非确定性 + 经验飞轮的双刃剑(T09)
同一 XSS 输入两轮结论相反(suspicious 0.55 → benign 0.78)。根因链:
第一轮研判经验沉淀入库 → 第二轮 Analyst 检索到历史经验「双 IOC 均为 RFC 保留段 →
规则测试/扫描器漂移而非真实攻击」→ 依据 IOC 可信度翻转判定。
**这个推理本身是对的**(203.0.113.x 确实是文档段, 不是真实攻击者), 暴露的是**评测设计
缺陷**(文档 IP 不该用于期望 malicious 的阳性样本), 但也揭示了产品风险:
- 经验库的「IOC 可信度」规则一旦沉淀, 会**压制 payload 层证据**(XSS payload 明确存在)
- 经验条目的适用边界没有约束(单案例经验泛化到所有同 IP 告警)
**建议**: 经验检索的注入应作为「参考」而非「依据」, 或对翻转既有判定的经验加人工确认关卡。

### 4.3 [低] 判定方差(T02)
Log4Shell 首轮 inconclusive(0.495)、二轮 malicious(0.85)。两次都提取了 CVE IOC,
差异在 Analyst 对「单次被拦尝试」的证据权重评估。temperature>0 + Critic 回环次数的
随机性造成。对边界案例属可接受方差, 但若用于自动化响应需注意。

### 4.4 [评测基建自身](三轮迭代修复, 记录备考)
SSE 块分隔符(\r\n\r\n vs \n\n)· 系统代理劫持 httpx(trust_env=False 解决)·
事件负载双层结构(告警嵌套 data / 邮件平铺)· 快速通道无 triage 事件 · elapsed 计时。
**教训: 评测器必须先被小样本冒烟验证, 再上全量。**

## 五、结论

安全告警分析模块的**核心研判能力扎实**: 五种真实厂商格式全兼容, 阳性判定分级
与证据强度匹配, IOC/MITRE 提取无误报零漏报, 邮件管线达到可用高质量。
**短板集中两点**: 主机安全类告警的域分流(可修, 关键词表补充), 判定稳定性
(经验飞轮的适用边界)。评测基建已沉淀为可重放的测试集与评测器
(`data/eval/`), 修复后可直接回归。
